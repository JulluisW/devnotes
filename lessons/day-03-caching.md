# Day 3: Rendering & Caching

**Goal:** understand how Next.js 16 decides what is prerendered, what is cached, and what runs per request, and use `'use cache'`, `cacheLife` and `cacheTag` to make DevNotes fast again.

---

## 1. Where we started: everything was ◐

After Day 2, every route was **◐ Partial Prerender**: only the shell + skeletons were built ahead of time, and **every visitor triggered DB queries** (~600ms each). Correct, but wasteful for blog posts that change maybe once a day.

## 2. The mental model: three kinds of content

With Cache Components, every piece of a page falls into one of three buckets:

| Kind | How you write it | When it runs | Where it ends up |
|---|---|---|---|
| **① Static** | plain sync code, module imports | build time | the static HTML shell |
| **② Cached** | `'use cache'` + `cacheLife(...)` | build time, then re-run per `revalidate` | **also** the static HTML shell 🎉 |
| **③ Dynamic** | uncached async I/O, `cookies()`, `headers()`, `searchParams`, short caches | every request | a `<Suspense>` **fallback** in the shell, real content streamed in |

The home page now has all three:

```
┌──────────────────────────────────────────────┐
│ ③ 🟢 "19 developers reading now"  ← streamed │   'seconds' cache → dynamic hole
│ ① Learn Next.js by building it.              │   static
│ ② Latest posts         │ ② 🔥 Trending        │   'blog' / 'minutes' caches
└──────────────────────────────────────────────┘
```

That's **Partial Prerendering (PPR)**: one response, one URL, but static, cached and dynamic parts mixed.

## 3. `'use cache'`: caching across requests

```ts
export async function getPostBySlug(slug: string) {
  'use cache';                         // ① cache this function's return value
  cacheLife('blog');                   // ② for this long
  cacheTag('posts', `post:${slug}`);   // ③ with these labels (for invalidation, Day 7)
  const post = await db.posts.findBySlug(slug);
  …
}
```

- **Cache key** = build ID + function identity + **serialized arguments**. `getPostBySlug('a')` and `getPostBySlug('b')` are separate entries. Variables captured from outer scopes become part of the key too.
- **Arguments and return values must be serializable**: plain objects, arrays, primitives, Dates, Maps, Sets. No class instances, no functions. Our DTOs from Day 2 are already perfect for this.
- **You can't call `cookies()` / `headers()` / read `searchParams` inside a cached scope**, including in helpers it calls. Read them *outside* and pass the value in as an argument (it becomes part of the key).
- Works on **functions** (data-level, like our DAL) and on **components** (UI-level, like `TagCloud`). A `'use cache'` at the top of a file caches every export.

### ❓ Your Day 2 question: `React.cache` vs `'use cache'`

| | `React.cache` (Day 2) | `'use cache'` (Day 3) |
|---|---|---|
| Lives for | **one request** | **across requests and users**, until revalidated |
| Purpose | dedupe repeated calls during a single render | avoid doing the work at all, and bake results into the build |
| Shared between users? | ❌ never | ✅ yes, so never put per-user data in it without passing the user as an argument |
| Needs `cacheComponents`? | no (it's React) | yes (it's Next.js) |
| Still useful for | per-request things you **can't** share: the current user from cookies (Day 9) | everything that's the same for every visitor |

That's why `getPostBySlug` dropped `React.cache` today: `'use cache'` also dedupes within a request (same args → same entry), and goes much further.

> ⚠️ `React.cache` inside a `'use cache'` function has its **own isolated scope**: values memoized outside aren't visible inside. Pass data in as arguments.

## 4. `cacheLife`: how long is "fresh"?

Every profile has three numbers:

| Property | Where | Meaning |
|---|---|---|
| `stale` | browser | the client router reuses it without asking the server (min 30s) |
| `revalidate` | server | after this, the next request gets the cached version **and** triggers a background refresh (stale-while-revalidate, like ISR) |
| `expire` | server | after this with **no traffic**, the next request must wait for fresh data |

Built-in profiles: `seconds` · `minutes` · `hours` · `days` · `weeks` · `max` (and `default`: 5m / 15m / never).

We defined our own in `next.config.ts`:

```ts
cacheLife: {
  blog: { stale: 300, revalidate: 3600, expire: 604800 }, // 5 min / 1 h / 1 week
},
```

…and it's **type-checked**: `cacheLife('blgo')` is a compile error (types are generated by `next dev` / `build` / `typegen`).

### The prerender thresholds (why LiveStats is a "hole")

A cache that's too short can't be safely baked into a build:
- `revalidate: 0` or `expire` < 5 min → **excluded from the prerender** (dynamic hole)
- `stale` < 30s → excluded (a prefetch would expire before you click)

Of the built-in profiles, only **`seconds`** (expire = 1 min) crosses that line. So `getLiveStats()` stays dynamic, while `getTrendingPosts()` with `'minutes'` (expire = 1 h) is prerendered and refreshed in the background every minute.

## 5. `cacheTag`: labels for on-demand invalidation

Time-based revalidation is a safety net. The real trigger is usually **"someone changed the data"**. Tags let a mutation say exactly what's outdated:

```ts
cacheTag('posts', `post:${slug}`);    // in getPostBySlug
cacheTag('posts', `tag:${tag}`);      // in getPostsByTag
cacheTag('authors', `author:${id}`);  // in getAuthor
```

On Day 7 a Server Action will call `updateTag('post:layouts-that-persist')` after an edit, refreshing just that post and leaving the other 99 cached. Design your tags now: **one broad tag (`posts`) + one precise tag (`post:<slug>`)**.

## 6. Reading the new build table

```
Route (app)                         Revalidate  Expire
┌ ◐ /                                       1m      1h    ← LiveStats keeps it ◐; Trending sets 1m
├ ○ /authors                                1d      1w    ← only 'days' caches
├ ○ /authors/maya                           1h      1w    ← 'days' author + 'blog' posts → shortest wins
├ ○ /posts                                  1h      1w
│ ├ ◐ /posts/[slug]                         1h      1w    ← the App Shell for slugs not built yet
│ ├ ○ /posts/why-server-components          1h      1w
```

Two rules to read it:
1. **A route takes the SHORTEST lifetime of everything on it.** `/authors/maya` uses `'days'` for the author but `'blog'` (1h) for their posts, so the page revalidates hourly.
2. **One dynamic hole makes a route ◐**, but only that hole is dynamic. Everything else on `/` is still static.

`◐ /posts/[slug]` is the **App Shell**: what an *unknown* slug gets instantly while its content renders on demand (and then gets cached, which is ISR).

## 7. What we measured 🔬

`npm run build && npx next start`, then:

| Test | Result |
|---|---|
| 6 visits to `/posts`, a post, an author, a tag | **0 DB queries**, 2–25 ms responses (vs ~600 ms+ on Day 2) |
| 3 visits to `/` one second apart | 3 queries: the `'seconds'` hole refreshing |
| 5 **simultaneous** visits to `/` | **1 query**: all five shared the same cache entry |
| Live badge across requests | `16 … 01:18:11`, `19 … 01:18:13`, `18 … 01:18:15` |

In **dev**, `'use cache'` works too (2nd visit to `/`: 1060 ms → 53 ms) but resets whenever you save a file, so measure caching with `build` + `start`.

## 8. Other tools you should know exist

- **`connection()`** from `next/server`: `await connection()` says "this component is intentionally per-request" (needed before `Math.random()` / `Date.now()` outside a cache).
- **`'use cache: private'`**: a cache that may read cookies/headers, stored only in the user's browser. For per-user data you still want prefetched.
- **`'use cache: remote'`**: a shared cache (Redis/KV) via a platform cache handler. On serverless, the default in-memory cache doesn't survive between instances.
- **`fetch()`**: not cached by default. Wrap the calling function in `'use cache'`.

### The two triggers (from #1)

| Trigger | API | Who fires it | When |
|---|---|---|---|
| **Time** | `cacheLife` | Next.js, automatically | `stale`: the **browser** reuses its copy, no request at all (`'minutes'` = 5 min, the "5 minutes" you felt when clicking links). `revalidate`: the **server** serves the old copy and refreshes in the background (`'minutes'` = 1 min). `expire`: no traffic for this long → the next request waits for fresh data. |
| **Event** | `cacheTag` + `updateTag` / `revalidateTag` | **You**, in code, when data changes | Day 7. Until something calls `updateTag('posts')`, tags do nothing. They're just labels waiting to be used. |

**Measured** with `next start` + `curl`, which has no browser cache, so `stale` doesn't apply. The build was about a minute old when we started.

| Request | DB queries | Why |
|---|---|---|
| t = 0 s | 1 | only the `live` hole |
| t = 31 s | 5 | page now older than 1 min → background regeneration (Trending + Latest) + `live` |
| t = 65 s | 1 | regenerated 34 s ago → still fresh; only `live` (10 s revalidate) |
| t = 67 s | 0 | `live` is 2 s old → served from cache |
